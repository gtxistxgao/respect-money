# Localization

The application supports English (`en`) and Simplified Chinese (`zh`). Catalogs live in `src/i18n/en.json` and `src/i18n/zh.json`, with matching keys and interpolation arguments. Most keys are their English source phrases; formatting helpers use stable keys such as `month.heading`. Non-English fixed strings belong only in the language catalog. Brand names, currency codes, provider identifiers and user data are not translated.

## Browser preference

Settings includes a Language selector. The default is Chinese to preserve the existing experience. The choice is stored under `respect-money-language` in localStorage; it persists across refreshes and synchronizes between tabs. When browser storage is unavailable, the selection still works for the current page session.

`src/web/language.ts` notifies React and updates the document language. Page titles, labels, accessible names, categories, countries, charts, month labels and currency formatting follow the preference. Switching language cancels and resets query caches so server messages are fetched in the new language. Financial values, stable category IDs, filters and stored records are unchanged.

## Server messages

Every browser API call sends `Accept-Language`. The server negotiates supported tags (including regional variants and quality weights), uses English for unsupported or absent headers, and returns `Content-Language` and `Vary: Accept-Language`. It does not mutate a global server locale; concurrent callers can use different languages.

Use `message(key, params)` for fixed server errors, rule explanations and background task messages. This produces a durable string containing the English key and interpolation arguments, compatible with existing SQLite string fields. `AppError` extends `LocalizedError`: its ordinary `message` is readable English for logs and CLI use, while `localizedMessage` preserves the key and arguments for response rendering and background persistence. Known Codex process errors use the same mechanism. Unknown errors return a generic localized message rather than exposing implementation details.

The response boundary translates only application message fields (`error`, `message`, `errors`, `lastError`, `reason`). It does not rewrite descriptions, notes, account names, raw payloads or overrides. AI-generated explanations are content rather than fixed interface copy and retain their original wording. Fixed Chinese messages saved by earlier versions are recognized using catalog templates; no financial data migration or reclassification is needed. Third-party authorization screens continue to be rendered by their provider.

Zod validation is rendered per request, including custom messages, constraints and known field labels. The CLI uses the English catalog. Existing local financial data and access tokens remain inside the ignored data directory.

## Adding copy or a language

1. Add the same key and placeholders to both catalog files. Use complete sentences when word order varies; avoid assembling translated sentence fragments.
2. Use `t(key, params)` in views, `message(key, params)` for persistent server messages, and `translate(locale, key, params)` when the locale must be explicit.
3. Never translate transaction IDs, category IDs, SQL fields, URLs, API property names, raw records or user-entered text.
4. For another language, add its catalog and register its locale, negotiation, formatting and selector option. Keep catalog key and placeholder tests passing.

Tests cover catalog parity, non-English source literals, language negotiation, interpolation, nested/legacy messages, concurrent API requests, validation and Plaid errors, persisted job messages, unchanged user data, and browser switching/reload. Browser coverage also checks the compact monthly overview, category panel order, success notice placement and both languages at mobile widths.
